# Korean Train Stats website

This public repository, [Bttlbmb/korean-train-stats](https://github.com/Bttlbmb/korean-train-stats), holds the static site at <https://koreantrainstats.com/>. It has eight kinds of page:

- the front page (`index.html`), with yesterday and the past 30 days;
- a train page for each train that ran in the past 30 days (`train/<id>/`);
- the all-trains page (`trains/`), with a row for each of those trains, which the front page’s header links to;
- the all-stations page (`stations/`), with a row for each station where a train reported an arrival in the past month, which the front page’s header links to;
- the all-journeys page (`journeys/`), with a catalogue of busy journeys and a search for trains between two stations;
- a journey page (`journey/<from>-to-<to>/`, the stations’ address names) for each journey in that catalogue, with figures for the whole journey, the delay by departure hour, and a table of its trains;
- a station page for each of those stations (`station/<address name>/`), which the all-stations page links to;
- a day page for each complete day since collection began (`day/<date>/`);
- a month page for each complete calendar month (`<year>-<month>/`, such as `2026-10/`), which the backend writes and the front page’s footer links (“Archive: October 2026”).

The pages are plain HTML, CSS, and JavaScript modules, with no framework. Their figures come from the JSON files in `data/`, which the backend’s exporter writes each night.

## Preview

```sh
python3 scripts/preview.py
```

The preview builds the site into `_site/`, which git ignores, and serves it at <http://127.0.0.1:8765/> on this machine only. It needs Node.js 18 or newer. Restart it to see a change.

The Korean version starts at <http://127.0.0.1:8765/ko/>. [The glossary](docs/korean.md) owns its wording, references, and review status.

## Build and publishing

`scripts/build.mjs` turns the data into finished HTML pages with the same modules the browser runs (`js/front.js`, `js/train.js`, `js/trains.js`, and `js/day.js`), so search engines and link previews read every page without running scripts. The build:

- copies the site’s files, leaving out hidden files, `artifacts/`, and the repository’s own guides and scripts;
- fills in both front pages and writes English and Korean train, train-list, all-stations, all-journeys, station, and day pages, a journey page for each journey in the all-journeys table, and `journeys/data.json`, the stops of every train that the all-journeys search loads;
- keeps the exporter’s English month HTML and builds Korean month pages from the archived day files through `js/month.js`;
- adds language links, reciprocal `hreflang` annotations, and a sitemap containing both languages;
- stops on a rendering error, incomplete month archive, or unresolved Korean station name so a partial translation does not publish.

`node scripts/build.mjs [output-directory]` recreates its disposable destination, `_site/` by default, so pages removed from the source data cannot remain in the published output. Use the finished build for link checks; raw exporter files are inputs rather than the complete bilingual site.

An address without a page returns `404.html`. A built train, day, or station page sits two folders down and the all-trains page one; each sets a `<base>` that points at the site root, so their links work like the front page’s; their skip link names their own address, because a bare `#main` would resolve to the front page. `app.html` only forwards old `app.html?train=<id>` and `app.html?day=<date>` links. The built files are never committed.

Push experiments to `main`. GitHub Actions checks them there. The daily job exports into `production`, whose own workflow builds and deploys the public site. A failed experiment on `main` leaves daily publishing independent.

To release a tested website change, start a separate checkout at the latest `origin/production`, cherry-pick the intended website code commits, then run the train check, build, and locale check against that checkout’s data. Push the tested commit with `git push origin HEAD:production`. If a daily update lands first, repeat from the new production tip. The backend replaces production history with one commit at each data refresh. Development history stays on `main`.

The nightly job in `../backend/scripts/collect_and_publish.py` starts from the latest `production` tree and stages only `data/`, `sitemap.xml`, and month folders. Website code released to `production` therefore survives subsequent exports. Keep production’s newer data when releasing code; the development checkout can contain older figures.

The domain is set in `CNAME`. Its DNS records are at Cloudflare and must stay “DNS only”: Cloudflare’s proxy stops GitHub from issuing the HTTPS certificate. GitHub redirects `https://bttlbmb.github.io/korean-train-stats/` to the domain.

The site makes no outside requests except to Google Fonts, which have local fallbacks.

## Data

`data/` holds the exporter’s output; never edit it by hand. The site reads `meta.json` (the complete-date range and any date still collecting), `days.json`, `windows/yesterday.json`, `windows/month.json`, `stations/index.json`, `trains/<id>.json`, and `days/<date>.json`. The backend’s `BUILD_NOTES.md` lists their fields and owns the definition of every figure. The exporter also writes `sitemap.xml` and the month folders at the site root.

## Interface

The backend’s `BUILD_NOTES.md` owns the metric definitions. “On time” always means within 5 minutes.

### Shared search controls

- **Station matching:** `stationSearchKey` in `js/utils.js` serves both the station directory and journey menus. It ignores case, spaces, and punctuation, reads “sh” as “s”, and removes a trailing “Station” or “역” after a nonempty name. Thus “Haengshin”, “Cheonan Asan”, and “서울역” find their source names. Matching uses normalization without an alias dictionary. Displayed names, stable station IDs, and the public English station values in URLs keep their source spelling.
- **Train numbers:** `trainNumberKey` and `trainNumberSearch` serve the all-trains page, station tables with controls, and a selected journey’s train list. Matching uses the complete number: `1` matches `00001` and full-width `１`, but not `11`. Invalid nonempty input produces no matches. Number search combines with the existing filters; station options remain based on train types and endpoints so entering a number does not clear them. In a journey panel, number search changes the departure list and its match count; the route-wide percentage continues to cover all services.
- **Layout:** the type boxes take a row of their own (`.trains-filters`, a grid), and the other controls share equal columns, at least 180 pixels wide, so the number box and the station menus line up on one row; a station-name search takes the full row. On phones two columns, with the number box and Sort by on full rows.
- **State:** `number` is the train-number URL key; `q` is the station-directory name key. Other keys are `types`, `from`, `to`, and `sort` where those controls exist. The page writes edits with `replaceState`, so typing does not create history entries. Returning from a train page or opening a shared link restores the filters, and language switching carries the search string. Journey `sort` controls the catalogue, while its train panel remains ordered by departure time.

### Front page

`index.html` is the front page. The build fills it from `js/front.js`; `js/start.js` refreshes the figures and date wording and binds the charts. The header holds the site name, a language switch, and three outlined navigation buttons: All trains, All stations, and All journeys. On phones the buttons share a row below the name and language switch. It reads `meta.json`, `days.json`, and the two window files. Under the two periods a lookup row holds one field and a Search button, the page’s one filled control; `js/start.js` answers it from `find.json`, which the build writes with the train IDs by number and the stations that have a page. It accepts what the train-number search and `stationSearchKey` accept, says so under the field when nothing matches, and falls back to the all-trains or all-stations page when `find.json` cannot be read.

- It has one row for Yesterday and one for the past 30 days. Each row has a 64-pixel share of stops within 5 minutes, one sentence, support lines (the typical delay when late, and for the 30 days the best and worst days), and a visual of the same height.
- **Yesterday** draws one dot per train in order of departure: late color when the train had a reported stop more than 5 minutes late, grey when it had no countable stops. A dot is two thirds of its grid step across, so the card shows between the dots. Hover and the arrow keys name a train. A click, or Enter on a selected dot, opens its page; on touch screens the first tap selects a dot and a second tap opens it. A screen-reader table lists the trains with a late stop.
- **Past 30 days** draws one bar per calendar day on a true 0–100% axis, in one green on a late-orange track by that day’s share within 5 minutes (a legend under the bars names both), and a short outlined stub for a day not collected. Hover, touch, and the arrow keys show a day’s share and late stops, and the bars open their day page the same way the dots open train pages. Each bar with data is a real `<a href="day/<date>/">`, so search engines follow it and a middle-click opens a new tab; the links stay out of the tab order, so the chart is one keyboard stop. With fewer than 30 complete days, the eyebrow says “N days from … to ….”
- The sentences carry no date or period (“of Korail train stops were within 5 minutes of schedule.”); each row’s eyebrow does: “Yesterday · Fri 13 Nov” when the newest complete date is yesterday in Korea time, otherwise “Fri 13 Nov”, and “Last 30 days from 15 Oct to 13 Nov” for the second row, the same wording as every header. The Korean page already worked this way.
- If any of the four requests fails, the built figures and footer remain as one dated snapshot. `data-from` and `data-to` on each period let the error path replace relative wording with absolute dates without fetched metadata (the English sentences have none, so only the eyebrows change). The fallback uses the built HTML, not browser storage. An uninitialized train-dot canvas stays hidden; the built daily bars become ordinary keyboard-accessible links. A single retry reloads all four files and restores the interactive charts. Repeated clicks cannot start overlapping loads; status messages and `aria-busy` expose the state to assistive software.

### Train page

`train/<id>/` is built from `js/train.js`; `js/app.js` adds the tooltips and the day strip. The header holds the site name, linking to the front page in the current language, and a language switch. The page always covers the past month.

- **Heading:** a back button to the front page, the title, a meta line (the scheduled departure and arrival times, the number of stops, and the window as “Last 30 days from 17 Oct to 15 Nov 2026 · 14 runs”, so the dates read as a deliberate 30-day window rather than all the data; every list, station and journey page uses the same “Last 30 days from … to …” wording from `span` in `js/utils.js` (Korean 최근 30일 (…부터 …까지) from `js/locale.js`, unreviewed), with the dates kept together on one line), and the definition of the percentages (“% = share of stops within 5 min”, one line each on phones), and a row of figures, each value at 20 pixels over its label (`stat` in `js/utils.js`; two to a row at 640 pixels and below, and the same on the station, journey, day, and list pages): the share of stops within 5 min, the days on time at the final stop, and the typical delay when late, and the longest delay (the greatest delay of any stop on any recorded day, Korean 가장 긴 지연), both left out for a train with no late arrival (127 trains now). A train with fewer than 10 recorded days has a muted line under them saying why the train and station lists show no share for it; its own figures stay, since the page shows the days behind them. On phones the route is a subtitle on its own line under the train, smaller and in grey, breaking before an arrow and never after it, and the lines under the title use the full width, below the back button; the day, month, and all-trains pages share that layout. A small grey map of South Korea with the route in ink sits to the right, drawn from the station coordinates and the outline in `js/korea.js`. It is decoration, so screen readers skip it, and it is left out unless every stop has coordinates.
- **Stop list:** titled “Delay at every stop” (the header gives the period), with one row per stop. Each row shows the scheduled time at the left (the arrival; at the origin, the departure, which the subtitle says: “scheduled times (departure at the first stop)”; and a small +1 after midnight), one dot per recorded day at its delay in whole minutes (green within 5 minutes, orange later, with a dashed line between 5 and 6 minutes and a thin grey line at 0 minutes, the schedule, labelled “0” and never “on time”, which the site defines as within 5 minutes; at 360 pixels and below the 5-minute label drops its unit so the two labels fit), and the share of days within 5 minutes at the right, or a dash when no arrival was reported. The origin has no arrival delay, so it has no dots and no share; its row carries the small “5 min” and “within 5 min” labels instead. Stop names link to their station pages (see the station-page decision). On phones the “departs” mark is hidden and the time column narrows. At 360 pixels and below the card padding and columns tighten so no stop name touches a dot, and the “5 min” label sits to the left of its line. The axis runs from −2 minutes to the 97th percentile of the train’s delays rounded up to 5 (never below 15); a day later than its end is drawn at the track’s end as a dot with a small arrow pointing out (the `.out` dots: one stack of up to 5 arrows 5.5 pixels apart at every width, extra columns stepping inward 12 pixels), the legend then adds “Later than N min”, and the row’s tooltip adds the longest delay. A day earlier than −2 minutes stays a plain dot at the start, because it is always within 5 minutes. The track ends 6 pixels before the share figure so an arrow keeps clear of it. Days with the same delay stack in a grid. In the browser, `packRailDots` in `js/app.js` lays the dots out again with the track’s real width, and again when it changes: a stack keeps its minute unless a neighbor needs the room, no dot crosses the dashed line or leaves the track (the arrow dots keep their place at its end and the others keep clear of them), tracks under 260 pixels use a tighter grid, and tracks under 100 pixels also use 3.8 pixel dots. Without JavaScript the built layout stays.
- **Day by day:** one cell per calendar day across the card, colored by the delay at the final stop, with a mark for a timetable change. It keeps calendar gaps, and its tooltips tell a day not collected from a day without a run and from an unavailable or missing record. The strip is one tab stop: the arrow keys step through the days and show each tooltip, and Escape clears it. A legend names the colors, with “No data” for a day without a value; on phones it is a grid of three columns. A screen-reader table lists every day.

### Day page

`day/<date>/` is built from `js/day.js` and has the train page’s header.

- **Heading:** a back button, the date as the title (the day, month, and year stay together on one line), a meta line (trains and stops), and four figures: stops within 5 min, trains with a late stop, typical delay when late, and the longest delay of the day (the biggest delay in the list below; both of the last two are left out when no stop was more than 5 minutes late). The card of the biggest delays says “Longest delay at any stop”. A train counts when it has a countable arrival.
- **How late stops were:** one bar split into within 5 min, 6–10, 11–20, 21–30, and over 30 minutes, sized by stops, so its green share is the heading’s figure. A legend under the bar names every part with its share, hover gives its stop count, and a screen-reader table lists them. On phones the legend has two columns with the shares aligned at the right.
- **Biggest delays:** up to 10 trains with the largest delay at any stop, only those more than 5 minutes late. Each row has the train, its route with scheduled departure and arrival times, the stop with the largest delay, the scheduled and reported arrival there, and the delay with a dot in its color. Korail reports a delay but no observed arrival time, so the reported arrival is the scheduled one plus the delay. A train links to its page only while it has one, so an older day lists some trains without a link. Under 760 pixels the route and stop columns are hidden and shown as a small line under the train, such as “Seoul → Busan · at Busan”, and the other cells align with the train line. On the day and month pages that line is 12 pixels, “at Busan” moves as a unit and drops the dot before it when it starts a new line, and the whole row opens the train (on the month page the date link still opens its day page); the day page also hides the reported arrival column, because the delay already gives it. A day with no late stop says so instead of showing a table.

### All-journeys page

`journeys/` is built from `js/journeys.js`; `js/app.js` loads `js/journeys-page.js` to add the controls and the search. A journey is two distinct stations in order, with one possible forward segment per train in its current timetable. Its share is the share of reported arrivals at the destination visit within 5 minutes, and its scheduled time (“Scheduled time” in the table, 예정 소요 시간 in Korean) is the median scheduled time between the two visits. Circular trains retain their clear segments, including travel into the return visit at Hongseong. Repeated visits are matched across timetable versions by station ID and visit number, so a final arrival is not confused with the starting departure. Multiple possible visit combinations exclude only that train’s contribution to the ambiguous pair. Search options, lists, and the selected-journey panel use the same segment rule.

- **Header:** the back button to the front page, “All journeys”, and a line with the number of journeys (every pair of stations that some train links, 10,116 in November 2026, not only the catalogue’s; the count under the controls reads “173 of 10,116 journeys”), the data period (“Last 30 days” and its dates), and the one definition of the page’s percentages (“% = share of arrivals at the second station within 5 min”); on phones each part takes its own line. It has no overall share, because journeys overlap and one arrival would count in many of them, and no station count, which All stations already gives.
- **Busiest and Least punctual** list five journeys each: the most trains, and the lowest share. Each row shows the train count and the share with a bar, and links to the journey’s page. Footnotes say what each list ranks.
- **Controls:** From and To are text boxes with matching station menus; hidden selects retain the actual choices. Typing searches the menu, and choosing an option updates the journey. The boxes narrow each other using `journeySegments`, the same rule as the results. Long options wrap within their fields. The share legend and dash explanation precede the selected-pair panel, so their meaning is available before the figures. See [Shared search controls](#shared-search-controls).
- **Selected journey:** the panel gives the share at the destination, service count, and typical scheduled time, then, at top right, a “Journey page” button when the journey has a page, then train-number search and departures in time order. The overall share needs at least 10 services and a reported arrival; otherwise the figure line says why in place of the percentage (“4 trains · too few for a share (10 needed)”, or “no arrival reported” with a dash when 10 or more trains have no reported arrival). Each train has its own destination share from at least 10 reported days. The first 40 matching trains show before Show all; expanding moves focus to the first newly revealed train. A journey that has a page also shows an outlined “Journey page ↗” button at the top right of the figure line (short “Page ↗” on phones); a journey without a page shows none. Number filtering leaves the overall figures unchanged and recalculates the matching count and row cap. A selected pair hides the catalogue table and its count; Reset restores them.
- **Catalogue:** built rows cover journeys with at least 40 services and a reported arrival. Columns show the journey, service types, scheduled duration, train count, and share. It starts with the most trains, is sortable, and shows 40 rows before a “Show 133 more journeys” button (the number of rows still hidden, never “all”, because the catalogue is not every journey). Selecting one station lists all of its supported journeys, including rare ones. Counts describe the selected scope rather than a fixed number of journeys. Durations use the middle sorted service time (upper middle for an even count), consistently in catalogue and panel, and show hours and minutes from 60 minutes. Rows of journeys with a page are real links to it, so modified clicks and middle-click work; a row of a journey without a page (shown when one station is chosen) opens its panel here, and an ordinary click on it is intercepted only on the same page. A note explains how to find journeys outside the busy catalogue (it does not repeat the 40-train rule that the Least punctual card states).
- **The data** is `journeys/data.json`, which the build writes from the train files (each train’s stops, times, and counts of reported arrivals) and the page loads when it opens. If it cannot load, the page retains the built list, explains which requested search failed, and offers Try again. The controls stay hidden until loading succeeds. The requested address remains intact, including when switching language, and a retry restores its filters.
- **The address** keeps the choices, such as `?from=Seoul&to=Busan&number=1`. The controls need JavaScript; the lists and the whole catalogue table are in the HTML. Error states retain the requested query until a successful retry can restore it.

### Journey page

`journey/<from>-to-<to>/` (Korean under `ko/`) is rendered by `renderJourney` in `js/journeys.js` for every journey in the all-journeys table. The build computes it from the train files with the delay bands (`journeyData(trains, stations, true)`), so visitors download nothing extra, and it stops if two journeys would share an address. The two directions of a pair each have a page when both qualify; the pages do not link to each other.

- **Header:** the back button, “Seoul → Busan” (the two names lead to their station pages and look like plain text), a line with the train count, the data period, and the definition of the percentages (“% = share of arrivals at Busan within 5 min”; one line each on phones, without the “·” between them, as on every page), and a row of figures: the share within 5 min, then within 10 and within 15 min, and the typical scheduled time. The cards do not repeat the definition or the period. Within 15 minutes counts every arrival up to 15 minutes, so it is not the sum of the chart’s bands.
- **By departure hour:** one stacked bar for each hour of departure from the first station, in the five-step delay scale (within 5, 6–10, 11–20, 21–30, over 30 minutes) with its legend; the share within 5 min is printed above the bar with a percent sign (the figures are left out when the columns are too narrow for them, as on phones, which `.hours-wrap` container queries decide by the number of columns; the tooltip and the hidden table keep them), the hour below it (the tooltip and the hidden table give the number of trains). The header line says what the number is; a line under the bars says what selecting a bar does, as the hint lines under the front page’s charts do. Each bar is a button that picks that departure hour in the table below (a second click clears it; the other bars dim, and the table scrolls into view when it is off screen). An hour needs 20 reported arrivals for a bar, otherwise it shows a dash and a grey track, and the tooltip says “fewer than 20 arrivals”. The buttons have their own labels, and a visually hidden table gives each hour’s trains, arrivals, and band shares. No text is smaller than 12 pixels, so the 18 bars of a long journey stay in one row at 320 pixels with a 3-pixel gap.
- **Find a train from A to B:** the all-trains page’s controls and table (`js/trains-page.js` reads the same ids): a train-number search, Departure hour and Arrival hour selects (hours that occur; `dep` and `arr` in the address, 0–23), a Sort by dropdown on phones and sortable headings elsewhere (train, arrival, and share; departure order is the default), the count and Reset, the share legend, and a row for each train: the train (a link), its departure, its arrival (+1 after midnight), and its own share at the destination (a dash under 10 recorded days, which its tooltip says). The first 40 rows show before “Show all N trains”. On phones departure and arrival read as one line under the train, from a separate cell that is hidden from screen readers; the separate cells stay in the accessibility tree.
- **Wording:** a review of the English and Korean strings on 15 November 2026 fixed the vocabulary of these pages. The header line reads “share of arrivals at Busan” where the station and list pages say stops, because these pages measure arrivals at one station; the table legend has no lead-in (`shareLegend('', null)` in `js/utils.js`). Figures carry their unit (“82% within 10 min”). The English “typical scheduled time” and the column “Scheduled time” say what Korean 예정 소요 시간 says: the median time in the timetable, not an observed time. The meta line says which trains the figures cover (“96 trains call at both stations”, 두 역에 모두 정차하는 열차 96편). Sort labels follow the all-trains page (“Departs, earliest”), band names are capitalized in the hidden table, and Korean puts a percentage after its label (see [the glossary](docs/korean.md)).
- **Not on the page:** Most and Least punctual lists, a map, train-type boxes, and a one-line best-and-worst summary.
- **Title and description:** “Seoul → Busan train delays and punctuality · Korean Train Stats” (“delays” alone when both words would not fit about 63 characters, `delaysTitle` in `js/utils.js`) and, in Korean, “서울에서 부산까지 열차 도착 지연”; the description gives the share, the window, and the number of trains, with shorter wordings (`fitting`) for long station names.

### Station page

`station/<address name>/` is built from `js/station.js`; `js/app.js` loads `js/trains-page.js` to add the controls. The address name is the station’s ID in `stations/index.json` when that is readable, otherwise its English name (see Addresses). A station gets a page when a train reported an arrival there in the past month. It has the train page’s header: the back button, “<Station> station” (Korean: the name and 역), a line with the number of trains that stop there, how many start there (a loop train counts once), and the number of reported stops with the data period, and a row of figures with the share of stops within 5 min and the figure for each train type that stops there (KTX, ITX with its services combined, Mugunghwa; Other is left out of the breakdown but counted in the total, and the breakdown is left out when only one type calls). The map is the train page’s, with a pin and a faint ring instead of a route, and is left out when the station has no coordinates or on phones.

- **Calls, not trains:** a row is one call of one train, from the train’s current timetable, so a train that calls twice (Hongseong on the ITX-Maum loop) has two rows, though the header, the description, the type boxes and the all-stations count count it once; where rows outnumber trains the table count says “stops” (Hongseong: 47 trains, 53 stops). A train that starts at the station has a time marked “departs”, no arrival, and a dash; one that ends there says “Ends here” under Final destination.
- **Find a train at <station>** holds the type boxes (left out when one type calls), a train-number search, a Going to dropdown, a Reset link (with, once a station is chosen that has a journey page, a link “<station> → <chosen> journey page” beside the count), the share legend (“Within 5 min”, “More than 5 min late”), and a table with time, train, Final destination (the train’s last stop), and share within 5 min with a bar. A share needs 10 reported stops; otherwise the row shows only a dash, with no bar. The first column is headed “Time” (Korean 시각), not “Arrives”, because a train that starts here shows its departure, marked “departs”; the phone sort option reads “Time” too. The table starts in order of time, so trains after midnight come last, and the headers sort it. On phones each row is two lines, with the time first. The all-trains destination filter reads Final destination and Any destination (Korean 종착역 and 전체 종착역) and matches only the last stop. The station page’s filter reads Going to and Any station (Korean 도착역 and 전체 역) and matches any station the train calls at after this one, the final stop included, so a row carries those stations in `data-to`, joined by `|` (`js/trains-page.js` reads both forms); a train that ends here is matched by “Ends here” only. The table keeps its Final destination column and sort option.
- **Busiest journeys at <station>** (`journeysCard` in `js/journeys.js`, added to the page by the build) closes every station page: its six busiest journeys by number of trains, however few, as the same rows the all-journeys lists use (three on phones, like every rank list). A “Show all” button was built and removed on 19 November 2026: its count covered only journeys with a page, so “all 24” was wrong for a station with 249.

- **The address** keeps the choices, such as `?number=1&types=KTX&to=Busan&sort=share_asc`. The controls need JavaScript and stay hidden without it; the full table is in the page.

### Addresses

Station and journey addresses use the station’s name, not its internal ID. Station IDs in `data/` are fixed once given, and 222 were given as `st-<number>` before an English name existed; used as addresses they would be opaque for good (`/station/st-100/`). So `js/addresses.js` renames the stations in memory as the build and the checks read the data (`stationAddresses`, `addressed`): a readable ID is kept (`daejeon`), an `st-<number>` ID becomes the slug of the English name (`okcheon`), and two stations that would share an address stop the build. The data files themselves keep the IDs. Each station or journey that took a name leaves a pointer page at its old address (a zero-second refresh and a canonical link to the new address; GitHub Pages cannot send a 301), which the sitemap leaves out and `check_locales.mjs` checks. A station whose English name later changes would change its address; give it an old pointer then.

### Search and link previews

- Each page has its own title, description, and canonical link. Train, day, station, all-stations, all-trains, all-journeys, and journey pages take them from `pageInfo` in `js/train.js`, `js/day.js`, `js/station.js`, `js/stations.js`, `js/trains.js`, and `js/journeys.js`, the front page from `frontInfo` in `js/front.js` (yesterday’s share and the 30-day share, so the snippet changes with the page), and Korean month pages from `js/month.js`; the exporter writes the English month pages’ into their markup. The front-page title is the question the site answers with the two words people search, “Korean Train Stats: how punctual are KTX and Korail trains?”. Inner titles put what tells pages apart first, since a tab shows only the first words: “Korail train delays, 13 November 2026” for a day, “October 2026: Korail train punctuality” for a month, “KTX 456 Mokpo → Seoul delays” for a train, and “Daejeon station delays and punctuality” for a station. A description opens with the page’s main figure and the window (“over the last 30 days”, `windowPhrase` in `js/utils.js` and `js/locale.js`, which names a shorter window instead), is about 140 characters or fewer in English (about 90 in Korean) so a search result does not cut it, and says “Korail” only in titles; the Korean descriptions keep 코레일, because Korean titles mostly lack it.
- `sitemap.xml`, expanded to both languages by the site build from the exporter’s records, lists the front page, the all-trains page, the all-stations page, and every train, station, day, and month page; `robots.txt` allows everything and names it. Submit `https://koreantrainstats.com/sitemap.xml` once in Google Search Console and Bing Webmaster Tools.
- The front page and each month page describe the data as a schema.org Dataset in JSON-LD, for Google Dataset Search: with `distribution` (links to the public JSON under `data/`), `dateModified` (when the export ran) and `measurementTechnique` (the 5-minute rule). The English front page also carries a `WebSite` block (name “Korean Train Stats”, alternate name 한국 열차 도착 지연 통계) so a search result can show the site’s name; Google asks for it on the home page only.
- Every page except the front page carries a schema.org BreadcrumbList (`breadcrumbs` in `scripts/build.mjs`, from `crumbs` in each `pageInfo`; the build adds it to the exporter’s English month pages), so a search result can show “All trains › KTX 237” instead of the address.
- Every page has link-preview tags (Open Graph and a large `twitter:card`) and a site image of 1,200 by 630 pixels: the logo, the site name, and the question the front page asks, `og.png` for English pages and `og-ko.png` for Korean ones (KakaoTalk and Naver build previews from it). The images carry no figure because messengers keep a preview for days, so a figure would go stale.

### Colors, legends, and type

- Train, station, and journey list tables retain column headings with `scope="col"` at every width. Mobile headings are visually hidden static text; their desktop sorting buttons stay out of the keyboard sequence, and the visible Sort by select handles sorting. Journey duration and train-count cells remain available to assistive software when their values also appear in the visible mobile summary.
- `tokens.css` holds the Porcelain palette: neutral greys, an ink-navy accent, and a terracotta delay ramp. Green means within 5 minutes, warm colors mean later, and grey is neutral. Share bars and daily punctuality columns use one green (`--ontime-mark`) on a late-orange track (`--d3`), rather than percentage-dependent shades. Delay cells, dots, and legends use the same green (`--ontime`; `--ontime-mark` repeats it). Headline figures use `--ink`, and `theme-color` repeats the canvas color.
- Every color scale has a legend that names what it measures and labels each step. The share legend reads Within 5 min and More than 5 min late (Korean 5분 이내 and 5분 넘게 늦음). The front page’s bars keep a lead-in (“Share of stops:”, on its own line on phones); the table pages leave it out because the header line defines the share. A card whose heading already names the measure, such as the month page’s day by day bars, leaves the label out.
- Share-legend producers are `js/utils.js`, `js/locale.js`, and the backend’s `share_legend` for English month HTML. Keep their definitions and color meanings aligned. Korean month headlines pool archived arrival counts, and their rankings combine the per-day top-ten lists; a missing calendar-day file stops that month’s build.
- On phones the back button and the site name have 44 pixel tap areas that extend beyond how they look, and the site name drops to 18 pixels at 360 pixels and below so it stays on one line.
- Names that link (trains, stations, and the dates in the month table) are in the text color in tables and lists and never underlined, at rest or on hover; a row's tint shows the hover. Navy is for links inside running text and for keyboard focus. Header buttons, the language switch, type boxes, dropdowns, the search box and the Show all button are 36 pixels tall on desktop and 44 on phones. The Reset link beside a table's count is text on the count's line, so it adds no height when it appears; an invisible margin gives it a 44 pixel tap area. ## Checks

- **Source data and rendering:** run `node scripts/check_trains.mjs` after changing a renderer or refreshing data. It checks page metadata, train dots, day buckets, list membership, counts, shares, and station totals against source files. It also checks station-name variants and journey lists and panels, and every journey page: its headline within 5, 10, and 15 minutes against a direct recount from the train files, a table row for each train, a hidden hour table that adds up to the journey’s trains and arrivals, unique addresses, a link to the other direction, and that every link from the all-journeys page reaches a page. Handwritten loop fixtures cover repeated visits, shifted ordinals, missing and unavailable reports, window boundaries, midnight offsets, and ambiguous pairs. A separate source-file recount checks every affected loop pair’s train, times, and arrival counts. Preserve these independent expectations when changing `journeySegments`.
- **Build and links:** run `node scripts/build.mjs` after changing any page, then `node scripts/check_locales.mjs`. The latter checks language pairs, internal links, resources, canonical addresses, language annotations, sitemap entries, matching chart figures, and calendar-month boundaries. GitHub Actions runs all three commands before deploying `production`.
- **Browser behavior:** the command-line checks do not exercise event handlers or the browser accessibility tree. Verify the affected pages in both languages at 360, 768, 1,280, and 1,440 pixels. Check matching, sort, Reset, row caps, shared URLs, Back from a detail page, language switching, empty results, and missing-value dashes. Long station options must fit their fields; modified route clicks must keep native tab and window behavior.
- **Failures and recovery:** block a front-page data request and `journeys/data.json` separately. Confirm that built content remains dated, requested journey parameters survive, retries do not duplicate controls, and recovery restores the requested filters and usable focus. A failed request must not be presented as an empty journey result.
- **Accessibility and layout:** inspect mobile table roles, complete column names, and the journey duration and count cells in the browser accessibility tree. Check keyboard sorting through the visible select and the absence of invisible header-button tab stops. Confirm that menus, figures, and errors fit without page overflow; use touch-browser checks when changing touch behavior. Browser-tree checks establish semantics, not a human screen-reader review.
- **Evidence:** keep one-off runners, screenshots, and logs under ignored `artifacts/`; they need not exist in a clean checkout. Record the result and checks in the commit message. Journey and train counts vary with the export and must not become fixed expectations in production-data checks.
